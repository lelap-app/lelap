# M2 Local library: design

Status: draft for approval. Milestone: [M2 in the roadmap](../../milestones/m2.md).

## Intent

Turn the M1 audio spike into a player for the maintainer's own audiobook files. They choose a
folder on the phone once; Lelap turns what is inside into books, reads chapters from the tags,
remembers the place in every book and keeps bookmarks. Real Library and Player screens replace the
throwaway test screen.

**Done when** the maintainer listens to their own files for a week in airplane mode without losing
their place.

## The maintainer's library

Looked at over adb on 2026-11-16: `Internal storage/Audiobooks`, 11 GB, 121 files, six folders.

- Audiobooks: one folder per book named `Author - Title`, holding one large mp3 (about 500 MB).
  ID3 tags carry title, album and artist on most, nothing on one; no chapter frames in any.
- Podcast series: two folders of episodes (62 and 22 mp3 files) named with `S01E01` or `E01` in
  the file name, with title tags, cover art and album tags that vary between seasons.
- Leftovers from the previous player: a `position.sabp.dat` in some folders and a statistics folder
  with a `.nomedia` file and no audio.

Test fixtures use invented names, not these files.

## Goals

- One library folder chosen through Android's folder picker, played in place (no copies).
- Books built from that folder: folders of parts and single-file books, with chapters from tags.
- The place in every book survives everything: pausing, swiping the app away, the service being
  killed, a reboot, a headphone Play press with the app closed.
- Bookmarks, speed per book, smart rewind, the existing sleep timer and call ducking.
- The SQLite schema through Drizzle with `profile_id` on every user-specific table and one default
  profile, ready for M9 and for M7 sync.
- Vitest, added with `packages/core` as the first TypeScript package, running in CI.

## Non-goals

- Downloads (M4), add-ons and LibriVox (M3), podcasts and Up Next (M5), web build (M6), sync (M7),
  the profile picker (M9), Android Auto browsing.
- Tags, playlists and smart lists. Their tables come with the milestones that use them, with
  `profile_id` from the start.
- More than one library folder in the UI (the schema allows several), "Add files", copying.
- Recognising a book that was moved or renamed on disk. A moved folder is a new book; the old one
  shows as missing with its progress kept.
- Search and metadata editing.
- Importing positions from the previous player's `position.sabp.dat` files (format undocumented).

## Anti-goals

- Losing the listening position in any situation the app can observe. This outweighs every other
  feature.
- Copying or re-encoding the user's audio.
- A scan that blocks the UI or re-reads every tag on every launch.
- Library logic (grouping, chapters, progress merging) in React components or in Kotlin. Playback
  behaviour that must work with the app closed (smart rewind, skip, the sleep timer) stays in
  Kotlin's tested `PlaybackRules`, as in M1; the web build gets its own player in M6 anyway.

## Constraints

- `AGENTS.md`: TypeScript strict, no `any`, named exports, few dependencies, English, CI rules
  (pinned actions, read-only permissions).
- `docs/brief.md` stack: Expo Router, NativeWind, Drizzle on expo-sqlite, zod, Vitest. Any change
  updates the brief in the same pull request.
- Supply chain (PR #4): every new dependency resolves to a version at least 7 days old; no
  `minimumReleaseAgeExclude` entries except urgent security fixes. Merge `main` before adding
  dependencies; re-run `pnpm install` rather than hand-merging the lockfile.
- Expo SDK 58, React Native 0.88, Media3 1.11.1, Pixel 10 Pro XL on Android 17 as the test phone.
- `apps/app/android` is generated by `expo prebuild` and not committed; native code lives in
  `modules/*`.

## Approaches

**Getting files in.** Considered: (A) one library folder read in place; (B) copying each import into
app storage; (C) a folder plus one-off files. **Chosen: A** (the maintainer's pick). Audiobooks run
to gigabytes, so copies would double storage and vanish on uninstall; one-off files can come later.

**Who owns the database.** Considered:

1. The app owns SQLite through Drizzle; the Kotlin playback service keeps a small position journal
   of its own that the app folds into SQLite when it starts. One writer, the same code on the web.
   Progress on screen can lag while the app is closed, but nothing is lost.
2. Native owns the database (Kotlin), JavaScript reads it through the bridge. Always current, but
   breaks "Drizzle everywhere" and needs a second database for the web.
3. Both write one SQLite file. Progress is current immediately, but two writers and a schema in two
   languages make every migration and the M7 oplog fragile.

**Chosen: 1** (the maintainer's pick).

## Architecture

```
apps/app            Expo Router screens, NativeWind; wires core to the native modules
packages/core       Drizzle schema + migrations, pure library logic, repositories; Vitest
modules/library     Kotlin: folder picker with persisted permission, folder listing, tags,
                    chapters, cover extraction
modules/audio       Kotlin: existing player + book identity, start position, position journal,
                    playback resumption
```

`packages/core` imports nothing from React Native or Expo. Repositories take a Drizzle SQLite
database object, so the app passes the expo-sqlite one and tests pass an in-memory one. Native
modules are reached through thin adapters in `apps/app` (for example `src/platform/library.ts`) so
M6 can add `.web.ts` versions.

### Schema

IDs are text UUIDv7 (time-ordered, safe to merge in M7). Times are integer milliseconds since the
epoch. Every table has `updated_at` for sync.

Shared across profiles (describe files on this device):

| Table           | Columns (main)                                                                                                                                               |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `library_roots` | `id`, `uri` (persisted tree URI), `name`, `added_at`, `last_scan_at`                                                                                         |
| `books`         | `id`, `root_id`, `location` (unique; see Identity), `kind` (`folder` or `file`), `title`, `author`, `cover_path`, `duration_ms`, `missing_since`, `added_at` |
| `book_files`    | `id`, `book_id`, `idx`, `uri`, `location`, `size`, `modified_at`, `duration_ms`, `title`                                                                     |
| `chapters`      | `id`, `book_id`, `idx`, `title`, `start_ms` (on the whole-book timeline)                                                                                     |

Per profile (every one has `profile_id` referencing `profiles.id`):

| Table             | Columns (main)                                                                                               |
| ----------------- | ------------------------------------------------------------------------------------------------------------ |
| `profiles`        | `id`, `name`, `created_at`. One row, the default profile, created by the first migration with a fixed ID.    |
| `library_entries` | `profile_id`, `book_id`, `speed`, `last_played_at`, `finished_at`                                            |
| `progress`        | `profile_id`, `book_id`, `file_location`, `file_position_ms`, `book_position_ms`, `updated_at`               |
| `bookmarks`       | `id`, `profile_id`, `book_id`, `file_location`, `file_position_ms`, `book_position_ms`, `note`, `created_at` |
| `settings`        | `profile_id`, `key`, `value` (JSON text)                                                                     |

A core test lists every table and fails if one outside the shared allowlist lacks `profile_id`.
The app resolves "the current profile" through one function that returns the default profile in
M2, so M9 only changes that function.

### Identity (builder check; my call)

A file's `location` is its path on the storage volume (the document ID inside the tree URI, for
example `primary:Audiobooks/Fiction/Dune/01.mp3`), not a path relative to the chosen folder. A
book's `location` is its folder's, or its file's for single-file books. So choosing a parent or
child folder in Settings finds the same books and keeps their places; the old root row is replaced.

Positions are anchored to a file: `progress` and `bookmarks` store the file's `location` and the
position inside it, plus the whole-book offset for display. When a rescan changes a book's files,
the place follows the same file; if that file is gone, it falls back to the whole-book offset. If
regrouping turns one book into several, progress moves to the new book that holds its file.

### Turning a folder into books

A pure, tested function in core takes the listed tree (paths, sizes, modified times, and per-file
tag facts) and returns books:

- A folder that directly contains audio files is one book; its files, in natural order
  (`2 < 10`), are the parts.
  This includes folders of podcast episodes: one book, episodes as chapters, played in file-name
  order (the maintainer's pick). M5 brings podcast-style series with per-episode progress and
  ordering by date.
- If those files each carry their own chapters (typically `.m4b`), each file is a separate book.
- A folder with no audio of its own whose subfolders are all named like discs (`CD 1`, `Disc 2`,
  `Part 3`) is one book, discs in order.
- Loose audio files directly in the root are one book each.
- Non-audio files are ignored, and folders without audio produce nothing. `.nomedia` is not a
  reason to skip a folder, since people use it to hide audiobooks from music apps.
- Title: album tag, else the folder or file name. For a folder book whose album tags disagree
  (`Bandeland`, `Bandeland 7`), the folder name. Author: album artist or artist tag, else the name
  of the parent folder when the book sits one level below an author-like folder.
- Cover: embedded picture, else `cover.*` or `folder.*` in the book's folder. Covers are saved as
  small files in app storage; `books.cover_path` points there.
- Audio types: whatever ExoPlayer plays from a file: mp3, m4a, m4b, aac, ogg, opus, flac, wav.

### Scanning

- First run shows an empty Library with "Choose your audiobooks folder". The folder picker takes a
  persistable read permission.
- A scan lists the tree (cheap), compares size and modified time with `book_files`, and reads tags
  only for new or changed files. It runs on app start and on pull to refresh, in the background,
  with a small "Scanning… 12 of 40" indicator; books appear as they are ready.
- Files that disappear set `books.missing_since`; the book stays, dimmed, with its progress and
  bookmarks. If the files come back, the book is whole again.
- If the persisted permission is gone, the Library says so and offers to choose the folder again.

### Chapters

- Embedded chapters: ID3 `CHAP` frames in mp3 and the chapter list in MP4/M4B (Nero `chpl` or the
  QuickTime chapter track). Use Media3's metadata extraction if it exposes them; otherwise small
  pure-Kotlin parsers, unit-tested on the JVM with fixture bytes (builder's call after a quick
  check).
- A multi-part book without chapter tags gets one chapter per part, titled from the part's title
  tag, else its file name, and prefixed with an episode code found in the file name
  (`S04E01 · Director`).
- A single-file book without chapter tags (all of the maintainer's audiobooks) has no chapters:
  the Player's scrubber covers the whole book, and the chapter buttons and sheet are hidden.
- **Risk to check on the device:** resuming deep inside a 500 MB VBR mp3. Without a Xing or VBRI
  header ExoPlayer estimates the byte offset from a constant bitrate and can land minutes away from
  the saved place. If the maintainer's files show this, enable Media3's index seeking for mp3
  (`FLAG_ENABLE_INDEX_SEEKING`) and measure how long a far seek takes.
- Chapters are stored on the whole-book timeline; core converts between book position and
  (file index, position in file) using `book_files.duration_ms`.

### Keeping the place

The key risk: the service keeps playing after the app is swiped away, when no JavaScript runs.

- `@lelap/audio` `load()` gains a `bookId`, the start file index and position, and the speed.
  Player state reports the `bookId`.
- The service writes a **position journal** (SharedPreferences, its own file): the current
  `bookId`, file index, position and wall-clock time, plus the loaded playlist (URIs, titles, book
  title, speed). It writes on pause, on part change, on seek, every 10 s while playing, on
  `onTaskRemoved` and `onDestroy`.
- The app reads the journal through a new bridge call on start and whenever it returns to the
  foreground, and while running it also saves progress from state events (throttled to 10 s and on
  pause). A journal entry is applied when it is newer than the stored `progress.updated_at`.
- **Playback resumption:** the service implements Media3's `onPlaybackResumption` from the
  journal, so a headphone or Bluetooth Play press with the app closed resumes the last book where
  it stopped.
- On app start, the last-played book is loaded paused at its position, so the mini player and lock
  screen are ready.
- **Smart rewind:** on Play after a pause, rewind 0 s if paused under a minute, 5 s up to an hour,
  15 s after that. It lives in Kotlin's `PlaybackRules` so it also applies to Play from headphones
  or the lock screen.

### With the app closed (builder check; my call unless noted)

- ⏮ and ⏭ on the lock screen, notification, headphones and Bluetooth skip back and forward by the
  skip interval (30 s by default), not by file or chapter (the maintainer's pick). The service
  maps Media3's previous and next commands to seeks.
- `load()` also passes the chapters, so the notification and lock screen show the current chapter
  title, and the journal keeps them for playback resumption.
- Settings the service needs (duck on calls, skip interval, smart rewind on or off) live in the
  `settings` table; the app pushes them to the service on start and on change, and the service
  keeps its own copy in SharedPreferences. The `settings` table wins.
- Speed per book travels in `load()` and the journal; a speed change from the app is saved to
  `library_entries` by the app.

### Screens

Expo Router with a root layout that opens the database, runs migrations, ensures the default
profile and reconciles the journal before rendering.

Library (`app/index.tsx`):

```
Library                              ⟳   ⚙
┌───────────────────────────────────────┐
│ [cover]  The Secret Garden            │
│          Ch. 7 · 3 h 12 min left   ▶  │   continue listening
└───────────────────────────────────────┘
Recent ▾
[cover] Title — Author          ▓▓▓▓░░ 45 %
[cover] Title — Author          New
[cover] Title — Author          ✓ Finished
[cover] Title — Author          Files not found   (dimmed)
─────────────────────────────────────────
[▪] The Secret Garden · Ch. 7          ▶    mini player
```

Sort by recent, title or author. Long press: mark finished or not finished.

Player (`app/player.tsx`, opened from the mini player or a book):

```
            [ large cover ]
          The Secret Garden
       Frances Hodgson Burnett
    Chapter 7: The Key to the Garden
  ────────●──────────────  12:04 / 31:40      within the chapter
   ⟲30    ⏮ Ch.     ▶     Ch. ⏭    30⟳
  1.25×      Sleep timer      + Bookmark      Chapters
          3 h 12 min left in book
```

Chapters and Bookmarks are sheets from the Player: tap to jump; bookmarks have an optional note and
can be deleted. Settings (`app/settings.tsx`): library folder (change, rescan), duck on calls,
skip interval.

The M1 test screen moves to a dev-only route until the remaining M1 call checks pass, then goes
with its LibriVox loader.

### Styling

NativeWind 4.2 with Tailwind CSS 3 (v5 is still a release candidate), which needs
react-native-reanimated. Colours from the M1 screen (`#0d0e11` background, `#f5b041` accent) become
theme tokens in `tailwind.config`.

### Tests and CI

- Vitest in `packages/core`: folder grouping, natural sort, timeline conversion, journal merge,
  smart rewind, the `profile_id` rule, and repositories against an in-memory SQLite (sql.js through
  Drizzle, which needs no native build scripts).
- Kotlin JVM tests in `modules/library` (chapter parsers, if written) and `modules/audio` (journal
  encoding and the rules for when it is written).
- CI: a `pnpm test` step in the `verify` job; the `android-unit-tests` job also runs the new
  module's `testDebugUnitTest` (its `modules/**` filter already covers it).
- A device checklist for the week test in `apps/app/README.md`: kill the app mid-chapter, reboot,
  Bluetooth Play with the app closed, airplane mode throughout, a missing-file case.
