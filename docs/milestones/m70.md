# M70 Release upkeep

Release and build work left out of M2, M18, M50 and M54.

- Skip `latest.json` when a release changes only JavaScript and the runtime version stays the same. (M18)
- No binary patches: every update downloads the whole bundle (about 6 MB). (M18)
- Raise `targetSdkVersion` to 37 as its own change; the Android 17 local network permission is only asked once it is. (M50)
- Apps from before M54 on 32-bit-only phones download the arm64 APK and fail on every start; the release notes of the first M54 release must tell them to install the `-armv7` APK once. (M54)
- The Gradle cache key comes from `pnpm-lock.yaml` only, so a Gradle-only dependency change keeps the old cache. (M54)
- F-Droid automatic updates need the base versionCode at the tag; until `UpdateCheckData` points at it, the two Builds entries per release are added by hand. (M54)
- The build-tools version used for signing isn’t pinned, and the printed certificate SHA-256 isn’t compared with `AllowedAPKSigningKeys`. (M54)
- Both direct legs set the `runtime` output. (M54)
- `verify-fdroid-apk.sh` with a local path as `SOURCE` works only with APKs given on the command line. (M54)
- The `apk` job in `ci.yml` is cancelled when `main` moves fast, so a cache save can be skipped. (M54)
- The M1 spike screen (`apps/app/app/dev/spike.tsx`) ships in release builds; gate it on `__DEV__` or remove it. (M2)

Done when a JavaScript-only release publishes no APK update and the signing job checks the certificate.
