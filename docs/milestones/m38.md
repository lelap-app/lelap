# M38 Add-ons in the app

**Status:** in progress.

Add-ons as a single JavaScript file that runs inside the app, for sources on the listener's own
network with no server for an add-on. The listener pastes the file's address in Settings →
Add-ons; the app reads its manifest in a sandbox with no network, shows what it can do, the hosts
it may reach and its code fingerprint, and keeps the code on the device (`local_addon_code`).

- **Sandbox:** a hidden WebView on Android, a scripts-only iframe on the web, each with a content
  policy that allows inline script and nothing else. `lelap.fetch` asks the app, which fetches
  only from the manifest's `sandbox.hosts` (`hostAllowed`), without the app's cookies.
- **Same protocol:** the app talks to it under `lelap-local://<id>/…` through the same routes as a
  web add-on, so catalogs, details, sources, badges and health work unchanged.
- **Limits:** 20 s per call and fetch, 5 MB per answer, 1 MB of code.
- **Docs:** “Add-ons inside the app” and “Making it fast” in the protocol docs; an example in
  `examples/in-app-addon/home-shelf.js`.

The idea first named QuickJS. A WebView/iframe sandbox gives the same isolation with an engine
already on every phone and browser, and no extra native interpreter to maintain; revisit if a
case needs tighter memory limits. Phone checks in [`m38-follow-ups.md`](../m38-follow-ups.md).

**Done when** an add-on file on the phone lists and plays books from a server at home and can't
reach anything else.
