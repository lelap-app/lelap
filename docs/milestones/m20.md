# M20 SDK on npm

`@lelap/sdk` builds to ESM and type declarations with `tsc`, Changesets versions it, and the `SDK`
workflow (`.github/workflows/sdk.yml`) publishes it with provenance through npm trusted publishing.
0.2.0 was the first release; 0.2.1 validated trusted publishing, and 0.3.0 and 0.4.0 went out the
same way. How to release: [`packages/sdk`](../../packages/sdk/README.md#releasing).

Set up on 2026-11-17:

- **npm:** a maintainer account with 2FA and the `lelap` organisation, which owns the `@lelap`
  scope. Usernames and organisations share one namespace on npm, so the account has its own name.
- **GitHub:** environment `npm`, limited to `main`, with required reviewers. It is separate from
  `release`, which only `v*` tags can use and which holds the signing keys; npm's trusted
  publisher names one environment.
- **Trusted publisher:** `lelap-app/lelap`, workflow `sdk.yml`, environment `npm`. The job needs no
  token; npm authenticates it through its OIDC token (`id-token: write`). The first publish used a
  short-lived granular token, since npm can only trust a publisher for a package that exists.

Worth knowing:

- Create a GitHub environment with its reviewers and branch rule before merging a workflow that
  names it: a job that names an unknown environment creates it with no rules and runs at once.
- A new npm package is reviewed: its first version showed as “Validating” for a few minutes and
  `npm view` returned 404 until then.
- `pnpm changeset version` runs locally. A bot opening “Version packages” pull requests would need
  `contents: write`, `pull-requests: write` and Actions allowed to open pull requests; only worth
  it if releases get frequent.
