# M144 SDK 0.6

`@lelap/sdk` is at 0.5.0 on npm and knows revision 9, while revisions 10 to 13 (M100, M102,
M118's `choice` settings and `settings` resource, M136's part transcripts, M135's OPDS fields),
the sealed config ID (M104), the test kit (M114) and series in the protocol (M127) wait as
changesets. Add-on authors can't use fields the published schema refuses. A third-party add-on
author also asked (2026-11-20) for the SDK-only items below; they need no protocol revision, so
they ship here, before [M152](m152.md).

- **Publish.** Run `changeset version`, read the generated changelog, and merge the version bump;
  `sdk.yml` publishes it with provenance. Check the protocol reference, the JSON Schema and
  `examples/` against revision 13, and make every example pass `lelap-sdk check`.
- **`waitUntil` in every handler's args**, for work after the answer: finishing a slow upstream
  search into the cache, refreshing a stale entry. `createAddon(...).fetch(request, env, ctx)`
  takes the Workers execution context; on Node and Deno the promise simply runs. Our own Workers
  add-ons use it where they now wrap it by hand.
- **Configure fields:** an optional `link` (`href`, `text`) shown beside a field, such as “Find
  your API key”, and `group`, a heading the page sorts fields under. No conditional fields: the
  second page (`choose`, M102) already covers fields that depend on others.
- **Credential helpers:** `fingerprint(secret)`, a short stable hash for cache keys that differ
  per account, and `log(event, fields)`, which takes only strings, numbers and booleans, so a
  URL with a key in it or an error that echoes one can't be printed by accident.
- **`mockFetch(routes)`** in the test kit: answers the routes given and fails any request none
  matches, so an add-on's tests never reach a real service.

**Done when** `npm view @lelap/sdk version` shows 0.6.x, a fresh project built from the docs alone
passes `lelap-sdk check`, and the examples use `waitUntil`, `log` and `mockFetch` where they
apply.
