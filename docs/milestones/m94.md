# M94 Tests against real servers

From Future goals, and the lesson of Android 17: some failures only show against the real thing.

## Remote code against real servers

The `remote-integration` job in `.github/workflows/ci.yml` runs `pnpm test:integration`
(`packages/core/integration`, its own Vitest config) against two servers in Docker:

- WebDAV: `rclone serve webdav` (rclone 1.71.2).
- S3: MinIO (RELEASE.2026-08-04). `minio/minio` is no longer on Docker Hub, so the image is
  `pgsty/minio`, the community-maintained build of the same server.

`scripts/test-servers.sh up|down` starts and removes them, in CI and on a laptop alike, on
localhost ports 18081 and 19190; both images are pinned by digest. Service containers can't pass
the command both images need, so the job starts them with the script instead.

Each run seeds its own folder with files made in the test: silent MP3s with made-up tags, a cover
image header padded past 64 KB, and names with spaces, accents, `&`, `#`, `%` and brackets. The
tests cover `checkWebdav` (the folder entered, a subfolder without a trailing slash, a wrong
password), `listWebdav` (paths, sizes, times, the books they make), playback from the listed URI,
Range reads (one byte of audio; a cover's first 64 KB and the cover guess that needs it),
`listS3` (paths, sizes, times, a listing of more than 1,000 keys, a wrong secret), pre-signed
reads with and without a Range header, and an expired link. Locally the tests take under a second
after the images are pulled.

The job runs on `main` and on pull requests that touch `packages/core/src/remote/**`, the library
code the tests use, the lockfile, the tests, the script or `ci.yml`.

## App on an emulator

The `emulator-smoke` job builds an unsigned x86_64 release APK (`scripts/emulator-apk.sh`, the
same release build as `scripts/unsigned-apk.sh` for another CPU type, never shipped) and runs
`scripts/emulator-smoke.sh` on an API 34 x86_64 emulator (`reactivecircus/android-emulator-runner`).
The release APK itself can't run there: its native libraries stay uncompressed inside the APK
(M54), and on an x86_64 emulator SoLoader only looks in `lib/x86_64`, so ARM translation never
gets the chance. The first CI run crashed at start for that reason (“couldn't find DSO to load:
libreactnative.so”). The job reads the pnpm and Gradle caches the `apk` job saves on `main` and
never writes them. The signed release builds and the `apk` job are unchanged; the `apk` job now
also keeps its APK as the `unsigned-apk` artifact for 3 days, to try a build on a phone.

The script signs the APK with a key made for the run, checks that its native code matches the
emulator's CPU type, installs it, starts the app, waits for Home and the tab bar, opens
`lelap://library` and waits for the empty Library's “Choose your audiobooks folder”, then fails
on a crash in the crash log or a fatal JavaScript error. It dismisses “System UI isn't
responding” dialogs, retries the install, and the whole test once (a pass on the second try
leaves a warning on the run); logs, the crash buffer and a screenshot are kept as the
`emulator-smoke` artifact. It refuses to run on anything but an emulator, since it uninstalls
Lelap first.

It runs under the `apk` job's rules, beside it rather than after it: on `main` and on pull
requests that change the build setup. It also runs on pull requests that change its two scripts,
and when CI is run by hand (`workflow_dispatch`, new in M94). Other pull requests that touch the
app don't run it, so they stay fast; run the workflow by hand on their branch to try one.

Scanning a folder and playing a file are not part of it: the folder comes from Android's folder
picker, which differs between Android versions and can't be driven reliably.
