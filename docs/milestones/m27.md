# M27 Add-on protocol v2

**Status:** in review. Settings pages for add-ons, add-on sign-in, health checks, protocol versioning. Details: [`next.md`](../next.md).

## What landed

- **Versioning:** `protocol` stays `1` (the major version, breaking changes only); the new optional
  `protocolVersion` is the revision, absent means 1. Revision 2 only adds optional fields and
  routes, so v1 add-ons and older apps keep working.
- **Behavior hints:** `behaviorHints.configurable`, `configurationRequired` and `health`. The old
  top-level `configurable` is still read.
- **Configure and sign-in:** the add-on's own `/configure` page; the app opens it with
  `?return=lelap://addon` and receives `lelap://addon?manifest=…` (or the listener pastes the URL or
  link). The app matches the manifest `id` and asks before adding or replacing; books, source choices,
  hidden-add-on lists and unsent scrobbles follow the new URL. No migration.
- **SDK:** `createAddon({ configure })` serves a form, encodes settings into a `/{token}/` URL prefix
  (AES-GCM with a secret), checks credentials through `check`, and passes `config` to handlers.
  `GET /health` is always answered; a `health` handler can report `degraded` or `down`.
- **App:** Settings → Add-ons shows a health dot, last response time and last error from real
  requests (in memory only), asks `/health` on open and on "Check now", and has a Configure button
  and a menu per add-on. `/addon` route handles the deep link on Android and the web.
- **Template, samples, docs:** the template has a settings page and `health`; the Node and Python
  samples answer `/health`; protocol reference and SDK guide describe the flow.
