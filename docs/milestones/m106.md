# M106 Speed and battery

Measured on the web and in Node, fixed where the numbers pointed, with budgets in the benchmark.
The phone's numbers (cold start, battery) are open checks below. What shipped:

- **The web app starts sooner.** Every screen is in the start bundle (`asyncRoutes` off for the
  web in `apps/app/app.json`, see [the brief](../brief.md#web)): the first screen no longer waits
  for its own chunk, after which React held it back. The database starts opening as soon as
  `src/db.web.ts` loads instead of after the first render, and its chunk files are read 16 at a
  time instead of one after another (`ChunkedFile.load`).
- **The Library reads 10,000 books once, not twice**, for its list and its lists' counts
  (`listBooksFrom`, `listPlaylistsWithCounts(db, profile, books)` in `packages/core`).
- **The web app keeps 47 MB less.** A save compares each chunk's fingerprint (two 32-bit hashes,
  `chunkPrint`) with the last save's instead of a 49 MB copy of the database (M80). That trade:
  a save takes about 18 ms longer at 10,000 books on a Mac.
- **Fewer wakeups while a book plays** (`modules/audio`, `Battery.kt`): the sleep timer ticks
  every 5 s until its last minute instead of every 250 ms; the chapter title on the lock screen is
  checked at the next chapter mark (at most every 30 s) instead of every second; with the app in
  the background, the app hears the player every 10 s instead of every second. Downloaded and
  local books no longer hold a Wi-Fi lock (`WAKE_MODE_LOCAL`); streams still do.
- **Budgets in the bench.** `pnpm --filter @lelap/core bench` fails when a row with a budget is
  over it; the table is below. It also times what the Library's first draw reads, opening and
  saving the web database, and what a save keeps in memory. It still runs only by hand, not in
  pull request CI.
- **Start marks.** `performance.mark` at each step of the start (`lelap:db-open`, `db-read`,
  `db-ready`, `root-ready`, `journal-folded`, `home-drawn`, `library-rows`; `src/startup.ts`), for
  reading in the browser console.

Looked at and left as is: the playback service writes the place every 10 s while playing (a
SharedPreferences `apply`, plus the listening tally), which is what keeps a place when the process
dies; the accelerometer is only on in the sleep timer's last five minutes; ExoPlayer's own wake
lock only while playing.

## How it was measured

The web numbers are headless Chrome 158 on an Apple M1 Max (32 GB), the production build
(`pnpm build`) served locally, a fresh profile, M43's test library (`seedBigLibrary`: 11,000
books with podcast episodes, 500 podcasts, a 49 MB database) written into the origin's storage
before the runs, the window 1280 × 900 (the wide layout). Each number is the median of 11 loads
after one warm-up, before and after builds served side by side and loaded in turns. Times are
from navigation start to the mark, read with `performance.getEntriesByType('mark')`; Home's
before has no mark, so the first moment “Continue listening” is on the page stands in for both.
Memory is `Runtime.getHeapUsage` after two garbage collections (`backingStorageSize` is
ArrayBuffers and the database). The machine was busy with other work (load about 7 on 10 cores),
so single loads vary by up to 0.1 s.

| Web, 10,000 books                       |                    Before |                     After |
| --------------------------------------- | ------------------------: | ------------------------: |
| Database starts opening                 |                    348 ms |                     72 ms |
| Database read and ready                 |                    499 ms |                    180 ms |
| First render                            |                    504 ms |                    185 ms |
| Home shows “Continue listening”         |                    646 ms |                    270 ms |
| Library shows its rows (at `/library`)  |                    847 ms |                    344 ms |
| ArrayBuffers held (database and copies) |                     97 MB |                     50 MB |
| JavaScript heap                         |                     21 MB |                     23 MB |
| JavaScript at start                     | 2,854 KB (765 KB gzipped) | 3,077 KB (821 KB gzipped) |

Steps, each measured the same way against the one before: opening the database at load, the
parallel reads and the single Library read took the Library from 847 ms to 700 ms; turning off
`asyncRoutes` took it from 683 to 381 ms and Home from 686 to 273 ms. The renderer's resident
memory wasn't measured reliably: the harness couldn't tell the page's process apart for certain.

The bench (`pnpm --filter @lelap/core bench`, Node 24, same Mac), medians:

| Bench row                            |   Before |   After |   Budget |
| ------------------------------------ | -------: | ------: | -------: |
| Library screen, first draw           | 116.5 ms | 75.5 ms |   200 ms |
| listBooks by recent                  |    42 ms |   41 ms |   120 ms |
| playlist counts                      |    57 ms |   56 ms |   150 ms |
| music suggestions                    |   7.6 ms |  7.5 ms |    30 ms |
| Home screen: continue, downloads     |   4.1 ms |  4.2 ms |    15 ms |
| carShelves                           |    80 ms |   78 ms |   240 ms |
| Podcasts screen: 500 subscriptions   |    18 ms |   17 ms |    60 ms |
| web start: sql.js opens the file     |     5 ms |    6 ms |    40 ms |
| web start: migrations, nothing to do |   0.5 ms |  0.5 ms |    10 ms |
| web save: kept between saves         |  49.1 MB |    0 MB |     5 MB |
| web save after one change            |   8.9 ms |   27 ms |    80 ms |
| groupIntoBooks                       |    34 ms |   47 ms |   250 ms |
| rescan, nothing changed              |   342 ms |  336 ms | 1,000 ms |

“Before” rows of the bench are the new rows run on the old code where they exist; groupIntoBooks
varies between 33 and 127 ms on the busy machine with no change to it. Budgets are about three
times the after numbers, so only a clear slide fails.

Wakeups while playing, counted from the tick plans in `BatteryTest.kt` (JVM, not a phone): a
30-minute sleep timer ticks 588 times instead of 7,200; an hour of a book with chapters every 20
minutes checks the chapter title 120 times instead of 3,600; in the background the app hears the
player 360 times an hour instead of 3,600. These are counts of work on the main thread while
ExoPlayer's wake lock already keeps the CPU awake, so the battery gain is small and is what the
checks below measure.

Not measured here: cold start and the Library on a phone, memory on a phone, battery. Android's
start runs the migrations and waits up to 1.5 s for the playback service's journal before the
first screen; both are timed by the checks below. Left for later in [M126](m126.md).

## Open checks

- [ ] (adb) **Cold start with 10,000 books on a mid-range phone, before and after.** Add the test
      library on a debug build (Settings → Developer → Test library), install a release build
      over it (`pnpm --filter @lelap/app exec expo run:android --variant release`), then five
      times: `adb shell am force-stop app.lelap` and `adb shell am start -W -n app.lelap/.MainActivity`.
      Note the median `TotalTime` and `WaitTime`, and the phone's model. Repeat with the release
      build of `main` before M106 on the same phone and data. The median is no worse after; under
      2 s (M43's target). Then remove the test library and repeat with a small library.
- [ ] (adb) **The Library's first rows with 10,000 books.** As M43's check: start
      `adb shell screenrecord --bit-rate 8000000 /sdcard/start.mp4`, `adb shell am start -W -n app.lelap/.MainActivity`,
      tap Library when the tab bar shows, stop after the rows, `adb pull /sdcard/start.mp4`, and count
      frames from the tap to the rows (÷ 60). Five runs, before and after M106.
- [ ] (adb) **Memory with 10,000 books:** open the Library and scroll to the end, then
      `adb shell dumpsys meminfo app.lelap | grep -E "TOTAL PSS|Native Heap|Dalvik Heap"`. Under 300 MB.
- [ ] (adb) **Battery, a downloaded book, screen off, one hour.** On Wi-Fi debugging
      (`adb tcpip 5555`, `adb connect <phone ip>`) so USB doesn't charge it:
      `adb shell dumpsys battery unplug`, `adb shell dumpsys batterystats --reset`, play the
      downloaded book, screen off, wait 60 minutes, then
      `adb shell dumpsys batterystats app.lelap > m106-download.txt` and `adb shell dumpsys battery reset`.
      Note the app's estimated power use (mAh), its CPU time (`Total cpu time: u=… s=…`), its wake
      locks and Wi-Fi lock time. The Wi-Fi lock time is zero; CPU time and mAh are lower than the
      same hour on the build before M106.
- [ ] (adb) **Battery, a stream, screen off, one hour.** The same commands with a LibriVox book
      streamed, into `m106-stream.txt`. The Wi-Fi lock is held while it plays; CPU time is lower
      than before M106.
- [ ] (adb) **Battery, casting, one hour.** The same commands while the book plays on a cast
      receiver, into `m106-cast.txt`. The phone's wake lock and Wi-Fi lock follow the receiver
      playing, as before M106.
- [ ] (adb) **Battery with a 30-minute sleep timer**, screen off: the same commands into
      `m106-timer.txt`; the app's CPU time over those 30 minutes is lower than before M106.
- [ ] (adb) While a downloaded book plays, `adb shell dumpsys wifi | grep -i -A3 "locks"` lists no
      lock for app.lelap; while a stream plays it lists one.
- [ ] (adb) With a book with chapters playing and the screen off, seek to five seconds before a
      chapter starts from the notification, wait ten seconds, and

- [ ] (adb) Play a book, press Home for two minutes, come back: the player shows the current

      the app: the book resumes within ten seconds of where it was.
