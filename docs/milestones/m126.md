# M126 Speed and battery 2

What [M106](m106.md) measured but didn't change. What shipped:

- **The Library rereads only the books that changed** (also [M118](m118.md)'s last item). SQLite
  triggers note each book whose row a list shows changes: the book itself, a profile's place or
  entry, its download, hiding it and a catalog link. One table, `book_changes`, keeps one row per
  book with a rising `seq` (migration 0031). `libraryBooks(db).read(profile)` in
  `packages/core/src/library/bookChanges.ts` reads every book the first time, then only those
  noted since; nothing changed gives the same array, and books that didn't change keep their
  objects. Past 2,000 changed books (a scan, a first sync) it reads everything again, as does a
  profile switch. The Library tab reads through it (`apps/app/src/libraryBooks.ts`); its sort,
  groups and lists' counts still run on each library signal, as tags and a kids profile's shelf
  aren't book rows. The triggers are made by `migrateSafely` after the migrations and dropped
  before them: drizzle-kit rebuilds a table to change it, which drops a table's triggers, and
  those that name `books` would make the rebuild fail. See the
  [brief's architecture](../brief.md#architecture).
- **233 KB less JavaScript at the web app's start** (3,212 KB to 2,979 KB; gzipped 864 KB to
  797 KB). The XML parser for feeds, OPML and server listings (fast-xml-parser, 116 KB) loads with
  the first one read: `parseXml`, `parseFeed`, `parseOpml`, `parseMultistatus` and
  `antennaPodFromOpml` are async. The bundled add-ons' code (107 KB) is a file of its own,
  `generatedCode.ts`, loaded when an add-on first runs (`bundledAddonCode`); their manifests stay
  in the start bundle. zod's `fromJSONSchema`, which the app never calls, is left out by a Metro
  shim (`apps/app/metro/zod-from-json-schema.js`). The service worker caches both new chunks, so
  the app works offline as before. Android keeps one Hermes bundle, so over-the-air updates don't
  change.
- **Start marks on Android.** The steps of the start (`db-migrating`, `db-migrated`,
  `root-ready`, `journal-folded`, `home-drawn` or `library-rows`) go to logcat as one line,
  `Lelap start: …`, in milliseconds since the bundle began (`src/startup.ts`), so the cold start
  check below can tell the migrations and the 1.5 s journal wait (`JOURNAL_WAIT_MS` in
  `apps/app/src/player.tsx`) apart. Whether to draw the first screen before the journal waits on
  those numbers: nothing was measured on a phone here.

Left out: saving on the web off the main thread (a save fingerprints 49 MB in about 27 ms on a
Mac); it is under Future goals in the [roadmap](../roadmap.md#future-goals).

## How it was measured

The bench (`pnpm --filter @lelap/core bench`, Node 24, Apple M1 Max, M43's 10,000 books), medians.
“One book changed” saves a place (with the triggers on) and draws the list again: the read and
its sort.

| Bench row                         |  Before |  After | Budget |
| --------------------------------- | ------: | -----: | -----: |
| Library refresh, one book changed | 47.3 ms | 1.7 ms |  40 ms |
| read of one changed book          |       – | 0.8 ms |        |
| saveProgress, with the triggers   |       – | 0.4 ms |        |
| Library screen, first draw        | 75.5 ms |  77 ms | 200 ms |
| rescan, nothing changed           |  336 ms | 358 ms |    1 s |

“Before” for the refresh is the whole read it replaces, run in the same bench. The web bundle
sizes are from `pnpm --filter @lelap/app build` before and after, the files in
`dist-web/_expo/static/js/web/`.

## Open checks

- [ ] (adb) **Cold start marks with 10,000 books.** With the test library on a release build,
      five times: `adb shell am force-stop app.lelap`, `adb logcat -c`,
      `adb shell am start -W -n app.lelap/.MainActivity`, then
      `adb logcat -d -s ReactNativeJS | grep "Lelap start"`. Note `TotalTime` and each step's
      median, and the phone's model, in this file: how long `db-migrated` and `journal-folded`
      take says whether the first screen should stop waiting for the journal.
- [ ] (adb) **A pause redraws the Library quickly.** With the test library, open the Library, play
      a book from it, pause: the book moves to the top of In progress at once, with its new place.
      `adb shell dumpsys gfxinfo app.lelap reset` before the pause and `adb shell dumpsys gfxinfo app.lelap`
      after: fewer janky frames than on the build before M126.
- [ ] (adb) **The Library follows every change.** In the Library: finish a book from its menu (it
      moves to Finished), hide one (it leaves the list), download a streamed one (its badge
      shows), match one with a catalog (its title and cover change), sync a place from a second
      device (its row moves). Switch profile and back: each profile's own places show.
- [ ] (adb) **An update from an older version keeps working.** Install the release before M126,
      add a few books and a place, then install this build over it: it opens, the Library shows
      the same books, and a new place shows in the list at once.
- [ ] (adb) **Bundled add-ons still run.** Add a Plex, Subsonic or HTTP folder server and scan it,
      on Android and in the web app: the books come in as before.
- [ ] (you) **The web app, first visit and offline.** In Chrome with a fresh profile, open the web
      app, subscribe to a podcast by its feed address and add an OPDS or WebDAV server: both work
      (the parser and the add-on code load on first use). Then go offline and reload: the app
      opens and the podcast's page shows.
