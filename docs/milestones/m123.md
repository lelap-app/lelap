# M123 Server sources 4

What [M100](m100.md) left out.

- **Add-ons without the screen.** The add-on sandbox was a hidden WebView inside the app's screen,
  so nothing ran it while the app was closed. A new module, `modules/headless`, starts the same
  page in a WebView that is never shown (`HeadlessSandbox.kt`), with the same settings: no file or
  content access, no storage or cache, no new windows, only `about:` addresses, and no network of
  its own. `sandbox/index.ts` uses it for a sandbox started while no host component is mounted
  (`screenMounted`); messages go both ways as with react-native-webview, so the page and the app's
  side are the same. When the screen goes while the player plays on, its sandboxes close and the next call starts one without a screen. The add-on still reaches the network only through the app's native fetch,
  with the M104 rules: declared hosts only reach public addresses, the home network only for
  addresses the listener typed, and a server's login only in that server's own sandbox. The brief
  records the choice over porting add-on code to Kotlin.
- **Places for add-on servers with the app closed.** The background refresh now sends what waits
  for Subsonic, Plex and Emby too (`apps/app/src/background.ts`, `flushServerPlaces`).
- **A place sent after each pause.** A book whose server keeps places carries `serverPlaces` in
  its `BookLoad`. When it pauses (not a stall while buffering), the playback service asks
  WorkManager, with a network, for a `places` server task 10 s later (`ServerTasks.kt`). The task
  runs the app's JavaScript task `lelap-server-task` through expo-task-manager, starting the app
  without a screen when it isn't running: it folds the journal and sends what waits. This covers
  Jellyfin and Audiobookshelf too, which waited for the hourly refresh before.
- **Located addresses for books started without the app.** A book from an add-on server that
  locates its files carries `locate`. When the service starts it by itself (Up Next, Next in
  list, Android Auto, playback resumption from headphones or the widget), it asks for a `locate`
  server task, which asks the add-on (`relocateBook` in `player.tsx`) and hands the service the
  new addresses; it moves the book there at its live place, as after a finished download. A
  download asks the add-on before it starts (`downloads.ts`).

Checked here: JVM tests for the sandbox rules (only `about:` loads, the message script quotes
everything that could end its string) and the server task names, and for `serverPlaces` and
`locate` through the queue and the journal; `pnpm check`, `pnpm test`, `pnpm lint` and
`pnpm build`; the app's Kotlin compiles (`:app:compileDebugKotlin`).
