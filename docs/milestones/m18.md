# M18 Updates over the air

- **App** (`apps/app/app.config.js`, `apps/app/src/ota.ts`): `expo-updates` with code signing
  (`apps/app/certs/certificate.pem`) and a fingerprint runtime version. A build without the
  certificate never loads code from the network. It checks on start and after 30 minutes in the
  background, and starts a new bundle on the next cold start. The channel is `beta` when “Beta
  versions” is on or the APK is a beta, else `production`.
- **Service** (`services/updates`, Worker `lelap-updates`, also a Docker image): answers the Expo
  Updates protocol from R2. A Worker rather than static files, because the protocol puts the
  signature in a header of the manifest part and picks the file by request headers; the bundles
  themselves go straight from R2.
- **Release** (job `ota` in `release.yml`, `scripts/ota.mts`): checks the bundle's runtime version
  against the APK's, signs the manifest and uploads it. Stable tags publish to `production` and
  `beta`, beta tags to `beta` only.

Forks and self-hosters generate their own key pair and certificate (see
[`docker/README.md`](../../docker/README.md)). If the key leaks or is lost, commit a new
certificate and release a new APK: devices only trust bundles signed for their APK's certificate.

Done when a JavaScript-only release reaches a phone over the air on both channels and a badly
signed manifest is refused.

## Setup

1. **Code-signing key pair.** Generate it on your own machine, with the private key outside the
   repository:

   ```sh
   cd apps/app
   npx expo-updates codesigning:generate \
     --key-output-directory ~/lelap-ota-keys \
     --certificate-output-directory certs \
     --certificate-validity-duration-years 10 \
     --certificate-common-name "Lelap"
   ```

   Commit `apps/app/certs/certificate.pem` (public). Keep `~/lelap-ota-keys/private-key.pem` in
   your password manager; `public-key.pem` is not needed. The certificate is part of the native
   fingerprint, so adding it starts a new runtime version: the first APK built with it is the first
   that takes bundles.

2. **CI secret** in the `release` environment:

   ```sh
   gh secret set OTA_SIGNING_KEY --env release < ~/lelap-ota-keys/private-key.pem
   ```

3. **Host for the Worker.** Add `UPDATES_DOMAIN` = `updates.lelap.app` as a variable in the `web`
   environment; the next push to `main` that touches `services/updates` (or a manual run of
   “Deploy services”) deploys `lelap-updates` with that custom domain, which also creates the DNS
   record. The Workers token needs R2 read on `lelap-downloads` (it already writes to it).

   ```sh
   gh variable set UPDATES_DOMAIN --env web --body updates.lelap.app
   ```

4. **Forks and self-hosters** generate their own pair, commit their own certificate, build with
   `EXPO_PUBLIC_LELAP_DOMAIN` (or `EXPO_PUBLIC_LELAP_UPDATES`), and either deploy the Worker or run
   the `updates` image (see [`docker/README.md`](../../docker/README.md)).

## Open checks

- [ ] (you) First bundle: install a signed release APK from a tag built with the certificate. Tag a
      JavaScript-only change (for example a text in Settings) as the next version. Open the app, wait
      a minute, close it fully, open it: the change shows, and Settings → Updates says “Running update
      …”. A fresh install of the new APK does not download the same bundle again.
- [ ] (you) Resume: with the app in the background for 30 minutes, publish another bundle; coming back
      downloads it, and it starts on the next cold start, not while a book plays.
- [ ] (you) Switch off: with “Download updates automatically” off, nothing downloads (check the Worker's
      logs); “Check” still does.
- [ ] (you) Beta: turn on “Beta versions” on a stable APK and publish a beta tag with the same runtime:
      the beta bundle arrives. A later stable tag reaches it too.
- [ ] (you) Bad signature: serve a record with a wrong signature (`wrangler r2 object put` a copy with
      one byte changed in `signature`): the app refuses it and keeps running the old bundle.
- [ ] (you) Native change: a release that changes native code (a new module) gets a new runtime version;
      older APKs don't get its bundle (the Worker answers `204` for their runtime).
- [ ] (you) Crash recovery: a bundle that throws on start makes expo-updates fall back to the previous
      one on the next launch.
