# Lelap: agent guidelines

Applies to every agent and contributor working in this repository. Nested `AGENTS.md` files add
rules for their own folder.

## What this is

Lelap is an open-source audiobook and podcast player. The app plays, downloads, remembers and
syncs; add-ons (stateless HTTP services returning JSON, modelled on Stremio's add-on protocol)
bring catalogs, metadata and audio sources. Android first, the same code on the web, and a
self-hostable backend. Decisions, principles and architecture are in
[`docs/brief.md`](docs/brief.md). Read it before making architectural choices. Milestones are in
[`docs/milestones/`](docs/milestones/), one file per milestone: status, summary and pull
requests in front matter, then the plan or a short record, then its open checks. The table in
[`docs/roadmap.md`](docs/roadmap.md) is generated from those files: when you start or finish a
milestone, change its front matter and run `pnpm roadmap`; never edit the table by hand, so
parallel pull requests don't conflict. `pnpm checks` lists every open check.

## Hard rules

- **Neutral core.** The app and first-party add-ons only connect to open sources (LibriVox, Open
  Library, Podcast Index, RSS) and storage the user controls (local files, WebDAV, Audiobookshelf).
  Never add code, docs, examples, tests or issue templates that target torrent indexes or services
  that resolve torrents or file-hoster links, and never name such services anywhere in the repo.
- **No add-on directory.** Don't add lists, links or recommendations for third-party add-ons.
- **Audio never touches our servers.** Services may proxy RSS feeds, cover images, chapters files
  and transcripts for the web app; they never proxy, cache or transcode audio.
- **Secrets stay out of the repo.** Keystores, API tokens and `.dev.vars` are ignored for a
  reason. Runtime secrets go to `wrangler secret put`; CI secrets go to GitHub environments.
- **English everywhere:** UI copy, docs, commits and pull requests.
- **No hard-coded hosts.** `lelap.app` and its subdomains come from configuration, so forks and
  self-hosters never edit source files.

## Commands

Node 24 (`.nvmrc`) and pnpm via Corepack (`corepack enable`). Run from the root:

| Task                  | Command                           |
| --------------------- | --------------------------------- |
| Install               | `pnpm install`                    |
| Landing page dev      | `pnpm dev:site`                   |
| App on a phone        | `pnpm android`                    |
| App dev server        | `pnpm dev:app`                    |
| Build everything      | `pnpm build`                      |
| Type-check everything | `pnpm check`                      |
| Test                  | `pnpm test`                       |
| Remote server tests   | `pnpm test:integration`           |
| Library timings (M43) | `pnpm --filter @lelap/core bench` |
| Lint                  | `pnpm lint`                       |
| Roadmap table         | `pnpm roadmap` (`--check` in CI)  |
| Open checks           | `pnpm checks` (`--adb`, `--you`)  |
| Format                | `pnpm format`                     |

Before opening a pull request run `pnpm format:check`, `pnpm roadmap --check`, `pnpm lint`,
`pnpm check`, `pnpm test` and `pnpm build`;
CI runs the same. pnpm 12 only runs dependency build scripts listed under `allowBuilds` in
`pnpm-workspace.yaml`; approve new ones with `pnpm approve-builds`.

**Supply chain.** `pnpm-workspace.yaml` only lets in package versions that have been published for
7 days (`minimumReleaseAge`), rejects versions with weaker provenance than earlier ones
(`trustPolicy: no-downgrade`) and keeps transitive dependencies on the registry
(`blockExoticSubdeps`). When `pnpm add` stops on a version that is too new, pick an older one or wait.
For an urgent security fix, add the exact `name@version` to `minimumReleaseAgeExclude` with a comment
saying why. Dependabot waits the same 7 days. Never weaken these settings to make an install pass.

**Migrations.** Generate them with `pnpm exec drizzle-kit generate` in `packages/core` on top of the
latest `main`; never write or renumber them by hand. When parallel pull requests both add one, the
one that merges later regenerates its migration after merging `main`. A dev database (the web
preview, a test phone) that already ran the old number must be reset, or it fails on start.

## Stack decisions

Don't swap these without updating `docs/brief.md` in the same pull request.

- **App:** Expo (React Native) with react-native-web, Expo Router, NativeWind for styling.
- **Native:** Kotlin Expo modules; Media3 for playback, WorkManager for downloads.
- **Data:** SQLite everywhere through Drizzle ORM; zod for validation and protocol schemas.
- **Backend:** TypeScript and Hono on Cloudflare Workers (D1, R2, Cache API); the same code runs
  in Docker for self-hosting.
- **Site and docs:** Astro, static output on Cloudflare Pages.
- **Monorepo:** pnpm workspaces. Changesets once the SDK is published.

## Code conventions

- TypeScript strict, no `any`. Named exports. Shared compiler options live in
  `tsconfig.base.json`.
- Comment the why, only where a reader would otherwise be surprised. One or two lines.
- Keep dependencies few, especially UI libraries that must work on both native and web.

## CI

GitHub Actions in a public repository:

- Pin every third-party action to a full commit SHA with the version in a comment.
- Default `permissions: contents: read`; widen per job only when needed.
- Never use `pull_request_target` together with a checkout of pull request code.
- The `android-unit-tests` job in `ci.yml` runs the Kotlin JVM unit tests on pushes to `main` and on
  pull requests that touch `modules/`, the app manifest files or the lockfile. Extend its path
  filter when a new native module or test location appears.
- `remote-integration` runs `packages/core/integration` against rclone's WebDAV server and MinIO in
  Docker (locally: `scripts/test-servers.sh up` first), on `main` and on pull requests that touch
  the remote code, the library code it uses, the lockfile, the tests or `ci.yml`. `emulator-smoke`
  installs the `apk` job's APK on an emulator and opens the Library (`scripts/emulator-smoke.sh`)
  whenever that job runs: on `main` and on pull requests that touch `modules/`, `apps/app`, the
  build setup or `ci.yml`.
- Deploy jobs use GitHub environments (`web` for the site and services, `release` for signed
  builds) so secrets never reach pull requests from forks.
- `release.yml` runs on `v*` tags: unsigned APKs per distribution and CPU type built with caches
  and no secrets, signed afterwards in the `release` environment with provenance, R2 and GitHub
  Releases, `latest.json` or `beta.json`, multi-arch images on `ghcr.io`, sync to production.
  Only runs on `main` save the caches it reads (the `apk` job in `ci.yml`); never let a job that
  holds secrets restore a cache.
- Release builds bundle JavaScript, which debug builds never do: Babel presets and plugins named
  in `apps/app/babel.config.js` (and by NativeWind's preset) must be the app's own dependencies,
  or pnpm's strict layout hides them.
